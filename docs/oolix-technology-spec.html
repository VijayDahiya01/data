Technology reference

What Oolix runs on

Every component, and the job it does. The stack is shaped by one constraint: a Buyer reaches a Data Partner’s customers without the Partner ever handing over their database, and without Oolix ever learning who those customers are.

The boundary explains the architecture

Most of the unusual choices below follow from a single line drawn through the system. Oolix holds campaigns, approvals and money. The Data Partner holds people. Nothing that identifies a person crosses from right to left.

Why there are two runtimes

Targeting has to happen where the customer data already lives, so the matching engine runs inside the Partner as a separate Go binary they operate themselves. Oolix sends signed instructions in; only a hashed token comes back. That is why this is not one application.

Oolix Cloud · the control plane
oolix/apps/api-gateway NestJS 11.2.1 · Fastify 5.11.3
The control-plane API. Holds campaigns, Partner approvals, activations and settlement, and signs the manifests each Agent pulls. Fastify over Express for latency headroom on the Agent’s polling path.
oolix/apps/web-portal Next.js 16.3.2 · React 19.2.8
One portal, four personas — Buyer, Data Partner, Network sponsor, platform operator — with navigation driven by permissions rather than a role check. Server-rendered so the access token never reaches the browser.
oolix/apps/worker Node 24.19 · SQS consumer
Queue consumers for domain events, plus scheduled monitors for Agent health and queue lag. Deliberately a long-running process, not serverless: a cold start in the ad-control path is a served-nothing.
oolix/packages/db Prisma 7.9.1 · PostgreSQL 16.10
Sole owner of the control-plane schema. Its guard test asserts what must never exist here — no customer table, no membership table, and no partner_user_id column anywhere.
Inside the Data Partner · their infrastructure
partner-agent Go 1.25
The decision engine, running on the Partner’s own machines. Verifies signed manifests, compiles audience rules against their data, materializes the matching members locally, and answers every ad request in under 100 ms. A single static binary because the Partner has to run it, not us.
Partner database PostgreSQL 16.10
Their customer attributes, consent records and materialized audiences. Oolix holds no credentials to it and never queries it — the Agent does, from inside.
Partner Redis Redis 7.4
Frequency counters and decision state for multi-replica deployments. Keys are hashes of activation + user, so even the Partner’s own cache holds no raw identifier.
partner/sdk-web TypeScript
The ad slot on the Partner’s page. Sends a placement id and nothing else; the Partner’s own backend resolves who the visitor is and asks the local Agent.
Shared contracts · both sides must agree
shared/contracts Zod 4.4.3
One definition of every cross-layer constant — reach buckets, error codes, the Partner matching algorithm. Two implementations of the same rule eventually disagree; this is the guard against that.
oolix/packages/manifest-schema ES256 / JWS
The signed activation manifest: approved rules, creative, budget, frequency cap, flight dates. The Agent verifies the signature before it will serve anything, so Oolix cannot widen an audience after approval.
oolix/packages/auth-rbac jose 6.2.10 · scrypt
Principals, permission checks, password hashing and sign-in tokens, and the Agent’s workload identity. The Agent mints a P-256 keypair inside the Partner and registers only the public half — Oolix cannot forge its signature.
oolix/packages/observability Structured logs
Logging with redaction and correlation ids. Redaction is not decoration here: a customer identifier in a log line would breach the same boundary the schema is designed to hold.

One ad request, end to end

Where each component actually earns its place, and where the boundary sits.

  1. Partner

    A visitor lands on a page they’re signed in to

    The SDK sends a placement id. The Partner’s backend resolves who the visitor is from its own session — Oolix supplies no identity, no cookie, no cross-site id.

  2. Partner

    Their backend asks the local Agent

    This is the only hop where a customer identifier exists, and both ends are inside the Partner.

  3. Partner

    The Agent decides locally

    Audience membership, consent for this campaign’s stated purpose, frequency cap, flight dates and ranking — all against the Partner’s own database, under a 100 ms budget.

  4. Oolix

    Only a hashed token comes back

    The Agent reports token_hash, activation, creative and placement. No user identifier, and only SHA-256 of the token — enough to attribute a click, never enough to reverse.

A deliberate deviation

The spec calls for TypeScript 7. It does not exist yet, so the build pins 5.9.3 and will move when 7 ships. Worth stating plainly rather than leaving someone to find the mismatch and wonder which is wrong.

The check that matters most

Phase 4 is adversarial by design. It plants a customer, serves them an ad, then hunts that identifier through every text and JSONB column in the Oolix database — 111 of them — and through the API logs. It has to come back empty. That single result is the product’s central claim, tested rather than asserted.
